# UI レビューの採点基準（rubric）

UI レビューサイクル（`.claude/skills/ui-review-cycle/`）で、レビュアー B（ui-reviewer）と品質担当 D（a11y-qa）が毎回最初に読む基準です。
周回ごとに採点がぶれないよう、ここに書いた言葉どおりに判定してください。

## 1. 重大度

| 重大度   | 定義                                                                               | 例                                                                                               |
| -------- | ---------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| Critical | 主要操作ができない。計算結果が誤って見える。表示が崩れて読めない                   | 375 幅で入力欄が画面外に出て操作できない／結果の数字が別の項目と重なって読めない                 |
| High     | WCAG 2.2 AA 違反。375 幅で横スクロールが出る。主要な数値やボタンが見落とされやすい | 本文のコントラストが 4.5:1 未満／タップ領域が 24×24px 未満で隣と近い／不正な入力に何の表示もない |
| Medium   | 使えるが品質を下げるもの。余白・揃え・階層・文言の不統一                           | カード間の余白が 16px と 24px で混在／見出しの文字サイズが画面ごとに違う                         |
| Low      | 細部の改善で、好みに近いもの                                                       | アイコンの線の太さ、強調色の微調整                                                               |

迷ったら、ユーザーが「その画面の目的（計算して結果を読む）」を果たせるかで決めます。果たせなければ Critical、果たせるが誤解や見落としが起きうるなら High です。

## 2. 指摘の書式（すべて必須）

```markdown
### [High] B-3 結果の年間手取りが 375 幅で折り返す

- 画面と幅: tool-salary-take-home / 375 / result-01.png
- 対象要素: 結果カードの「年間手取り」の数字（components/tools/salary-take-home/ResultPanel.tsx の大きい数字）
- 問題（Before）: 「6,035,412円」が 2 行に折り返し、桁の区切りが行をまたいでいる
- 修正案（After）: 375 幅だけ `text-3xl` を `text-2xl` にし、`whitespace-nowrap tabular-nums` を付ける
- 理由（Why）: Nielsen heuristic #8 - Aesthetic and minimalist design（主役の数字は 1 行で読めるべき）
```

- 指摘 ID は担当の頭文字と連番（B-1、D-1 …）。次の周回で「直ったか」を ID で追う
- 理由の出典は 1 つだけ: Nielsen の 10 原則（番号と名前）、WCAG 2.2 の達成基準（番号）、Apple HIG / Material Design の項目名、Web Interface Guidelines の項目
- 書いてはいけない例: 「全体的にもっと洗練させる」「余白を整える」「モダンにする」（対象要素も値もない）

## 3. 観点（11 項目）

各項目を ◎（問題なし）／○（Low のみ）／△（Medium あり）／×（High 以上あり）で付けます。

1. 情報の階層（最初に目に入るのが主役の数字か）
2. タイポグラフィ（サイズの段階、行間、数字の等幅）
3. 色とコントラスト（WCAG 1.4.3 / 1.4.11、トークン以外の色）
4. 余白とリズム（8px 単位、カード内外の一貫性）
5. 整列（左端・数字の右揃え・グリッド）
6. 数値の読みやすさ（単位、桁区切り、強調の一貫性）
7. フォーム（ラベル、ヒント、入力形式、タップ領域）
8. フィードバックとエラー（入力の反映、不正入力の伝え方）
9. レスポンシブ（375 / 768 / 1440 で崩れ・横スクロールがないか）
10. ダークモード（コントラスト、色の対応漏れ）
11. 一貫性（同じ部品が画面ごとに同じ見た目・同じ言葉か）

## 4. 10 点満点の採点

design-review スキルの 0〜4 点の帯（`.claude/skills/design-review/references/review-rubric.md`）を先に決め、次の表で 10 点満点に直します。

| design-review の帯              | 10 点換算   | 帯の中での決め方                       |
| ------------------------------- | ----------- | -------------------------------------- |
| 4/4 ship-ready                  | 10 または 9 | Low が 1 件もなければ 10、あれば 9     |
| 3/4 solid, with specific tweaks | 8 または 7  | Medium が 0 件なら 8、1 件以上なら 7   |
| 2/4 needs work                  | 6 または 5  | High が 0 件なら 6、1 件以上なら 5     |
| 1/4 significant rework          | 4 または 3  | Critical が 0 件なら 4、1 件以上なら 3 |
| 0/4 broken                      | 2 以下      |                                        |

合格ライン 8 点は「構成と仕上げはおおむね正しく、残りは Low の磨き込みだけ」という意味です。

## 5. 合格条件（すべて満たしたら合格）

判定は **その PR の範囲** で行う（2026-11-28 ユーザー決定）。PR の範囲 = その PR で変えたファイルと、その変更による退行。
PR より前からあるページ固有の問題は、担当する後続 PR に送り、記録の「後続 PR に送るもの」に残す。B は「PR 範囲の採点」と「画面全体の採点（参考）」を両方出す。合格ラインの 8/10 は PR 範囲の採点に当てはめる。

- Critical と High が 0 件（B と D の合計）
- B の採点が 8/10 以上
- 3 つの幅すべてでレイアウト崩れ・横スクロールがない
- 主要操作（入力、計算結果の更新、共有リンク）が動く
- `pnpm typecheck`、`pnpm lint`、`pnpm test`、`pnpm build` が通る
- `pnpm test:a11y` の違反件数が基準（`e2e/a11y-baseline.json`）より増えていない
- 視覚回帰の差分が、今回の改修で意図した画面だけに出ている
- 6 つの制約を守っている（計算ロジック・URL・共有リンク・企業データ・ダークモード・小さな PR）

## 6. レビュー記録の書式

オーケストレーターが B と D の返答をまとめ、`docs/ui-reviews/<feature>/cycle-<N>.md` に保存します。

```markdown
# <feature> レビュー記録 cycle-<N>

- 日付:
- 対象コミット:
- 撮影: reviews/<feature>/cycle-<N>/（幅 375 / 768 / 1440、状態 …）
```
